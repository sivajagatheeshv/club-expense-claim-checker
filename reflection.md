# Project Reflection: Club Expense Claim Checker

Building the Club Expense Claim Checker fundamentally changed how I think about integrating large language models into real-world financial workflows. Before starting this project, it was tempting to treat an LLM as an end-to-end decision maker that could read an expense note, calculate totals, and decide whether a claim should be paid. Writing the one-page specification first forced me to separate probabilistic language understanding from deterministic policy enforcement before writing a single line of Python.

The most important technical lesson I learned was never to trust raw LLM output without independent verification. During testing, I saw how easily an LLM can attempt mental math on notes like “500 per person for 6 players” or get distracted by prompt injections such as “approved, pay immediately” when no receipt is attached. By writing `numbers_in()` and `check_facts()` in Python to verify that extracted numbers appear verbatim in the raw text and that receipt keywords are present without negation, I ensured the model only translates messy human text into structured JSON while Python retains strict control over validation.

Designing the sequential rule engine in `decide()` also highlighted how subtle ordering bugs can distort financial tracking. Evaluating `needs_more_info` and `needs_bill` before checking budgets prevents unverified claims from consuming category limits. Similarly, using dictionary tuple keys—`(club, category)` for running budgets and `(club, category, date)` for daily totals—allowed the program to catch same-day split claims exceeding Rs. 5,000 cleanly without complex database dependencies. Handling free-tier Gemini API rate limits and model availability through automatic fallback and retry pauses also taught me how to make AI tools resilient in production-like console runs.

Finally, building the Judgment Framework reinforced the importance of human-in-the-loop governance. Because a false approval carries direct financial risk while a false flag only delays review, the system is intentionally designed to fail safe toward `review.csv`. Above all, keeping the faculty treasurer as the final human checkpoint who signs every payment after inspecting the physical bill ensures accountability stays with a person rather than an algorithm. Testing the tool against both standard claims and red-team inputs proved that small, single-purpose functions make debugging straightforward and transparent. Overall, this project showed me that reliable AI engineering depends far more on clear specifications, strict validation boundaries, and human oversight than on the prompt alone.
